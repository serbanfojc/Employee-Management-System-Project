# Employee Management System
A java application for managing employee records at scale, built with core OOP principles across two development stages. Loads and processes 1000+ records from CSV, supports three employee types through inheritance, and provides sorting, querying and data export functionality.

# What it does
- Parses a 1000 row CSV dataset into typed Java objects at runtime
- Manages three employee types - FullTimeEmployee, PartTimeEmployee, Contractor -> all extending a shared Employee base class with 10 validated fields
- Sorts employees by ID (natural ordering via Comparable) or alphabetically by name (custom Comparator)
- Detects duplicate records using HashSet with custom equals() / hashCode() logic tied to employeeID
- Groups and counts employees by department using HashMap with putIfAbsent() and getOrDefault() for null safe operations
- Queries employees by hire date range and top-N salary using Java Streams
- Exports filtered results back to CSV
- Skips and logs malformed rows without crashing - invalid data is caught per line and reported

# How to run
Requirements: Java 17+, VS Code with Java Extension Pack (or any Java IDE)
# Clone the repo
git clone https://github.com/serbanfojc/employee-management-system.git
cd employee-management-system/EmployeeManagementSystem

# Compile from src/ into bin/
javac -d bin src/*.java src/model/*.java

# Run from the EmployeeManagementSystem/ directory
# (so relative path "data/dataset_1000.csv" resolves correctly)
java -cp bin App

# Key Design Decisions
Inheritance hierarchy - FullTimeEmployee, PartTimeEmployee, and Contractor each extend Employee, sharing 10 common validated fields while adding their own type-specific ones (e.g. hoursPerWeek capped at 40 for part-time, contractEndDate validated to not be in the past for contractors). This avoids duplicating validation logic and lets the CSV loader dispatch to the correct constructor based on the employeeType column.

Defensive coding throughout - every setter validates before assigning. Null and empty checks on strings, range checks on numerics (salary >= 0, yearsOfExperience >= 0, hoursPerWeek between 0-40), and temporal logic checks (hireDate not in the future, contractEndDate not in the past). The CSV loader wraps each row in a try/catch so a single bad record never halts the load.

Comparable vs Comparator - Employee implements Comparable<Employee> for natural ordering by employeeID (the unique business key), used with Collections.sort(). EmployeeNameComparator provides an alternate alphabetical sort without modifying the class, following the open/closed principle.

equals() and hashCode() via employeeID - both methods are based on employeeID as the unique identifier. This is what makes HashSet<Employee> for duplicate detection and HashSet<Employee> for unique-employee extraction work correctly. Inconsistent hashCode / equals implementations are a common bug in Java collections work — implementing them consistently here prevents silent failures.

HashMap with null-safe patterns - DuplicateDetector uses getOrDefault() for counting and putIfAbsent() for grouping, avoiding NullPointerException on first-seen keys without explicit null checks.

Streams for queries - EmployeeQueries uses the Java Streams API to filter by date range and sort by salary in two short, readable pipelines. This keeps query logic declarative and easy to extend without additional loop boilerplate.

Development stages

Stage 1 - Core OOP model: Employee base class with 10 validated fields, three subclasses, CSV loader for 10-row sample, Comparable ordering by ID, EmployeeNameComparator, App.java demonstration.

Stage 2 - Collections and queries: scaled CSV to 1,000 rows, added equals() / hashCode(), DuplicateDetector with HashSet / HashMap, EmployeeQueries with Java Streams (date range, top-N salary), CSV export, JUnit 5 tests.
